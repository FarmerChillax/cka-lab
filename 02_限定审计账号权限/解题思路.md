# 第 2 题：解题思路

## 关键技术难点

1. Pod 日志使用 `pods/log` 子资源，普通的 `pods` 读取权限不足以读取日志。
2. ConfigMap 只允许读取 `runtime`，需要在对应规则中使用 `resourceNames`，且不能授予 `list` 或 `watch`。
3. 使用命名空间级 Role 和 RoleBinding 限定作用域；验证时需模拟 `cka-lab/auditor`，同时检查允许和拒绝的操作。

## 排查与实施顺序

1. 列出目标身份、命名空间、资源、子资源和每种资源允许的动词。
2. 创建命名空间级 Role，并将 Pod、Pod 日志、指定 ConfigMap 分为独立规则。
3. 通过 RoleBinding 将 Role 绑定到现有 ServiceAccount `auditor`。
4. 使用 `kubectl auth can-i --as` 验证正反权限；检查写操作和其他命名空间是否仍被拒绝。

## 答案详解

### 参考清单

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: auditor
  namespace: cka-lab
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
- apiGroups: [""]
  resources: ["pods/log"]
  verbs: ["get"]
- apiGroups: [""]
  resources: ["configmaps"]
  resourceNames: ["runtime"]
  verbs: ["get"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: auditor
  namespace: cka-lab
subjects:
- kind: ServiceAccount
  name: auditor
  namespace: cka-lab
roleRef:
  kind: Role
  name: auditor
  apiGroup: rbac.authorization.k8s.io
```

保存为 `auditor-rbac.yaml` 后执行 `kubectl apply -f auditor-rbac.yaml`。

`pods/log` 必须单独授权；`resourceNames` 将 ConfigMap 的 `get` 限于 `runtime`。
