# 第 8 题：解题思路与答案详解

## 关键技术难点

1. `apiextensions.k8s.io/v1` 的 CRD 需要结构化 OpenAPI schema；在 `spec` 下标记 `required`，并给每个声明字段标明类型。
2. `status` 是子资源；开启后，普通 spec 写入与 status 写入分开。
3. `additionalPrinterColumns` 的 JSONPath 指向实例字段，不是 CRD 本身的字段。

## 解题思路

先定义 CRD 的名称、版本、scope 和 schema；等待 Established，再创建实例。最后分别检查打印列、schema 对非法值的拒绝，以及 status 子资源写入结果。

## 答案详解

保存为临时文件 `widget-crd.yaml`：

```yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: widgets.lab.cka.example
spec:
  group: lab.cka.example
  scope: Namespaced
  names:
    plural: widgets
    singular: widget
    kind: Widget
    listKind: WidgetList
  versions:
  - name: v1
    served: true
    storage: true
    schema:
      openAPIV3Schema:
        type: object
        required: [spec]
        properties:
          spec:
            type: object
            required: [image, replicas]
            properties:
              image:
                type: string
                minLength: 1
              replicas:
                type: integer
                minimum: 1
                maximum: 5
          status:
            type: object
            properties:
              readyReplicas:
                type: integer
                minimum: 0
    subresources:
      status: {}
    additionalPrinterColumns:
    - name: Desired
      type: integer
      jsonPath: .spec.replicas
```

保存为临时文件 `widget-demo.yaml`：

```yaml
apiVersion: lab.cka.example/v1
kind: Widget
metadata:
  name: demo
  namespace: cka-ext
spec:
  image: nginx:1.27.5
  replicas: 3
```

应用并验证：

```sh
kubectl apply -f widget-crd.yaml
kubectl wait --for=condition=Established crd/widgets.lab.cka.example --timeout=60s
kubectl apply -f widget-demo.yaml
kubectl -n cka-ext patch widget demo --subresource=status --type=merge \
  -p='{"status":{"readyReplicas":2}}'
kubectl -n cka-ext get widgets
kubectl -n cka-ext get widget demo -o yaml
kubectl -n cka-ext patch widget demo --type=merge \
  -p='{"spec":{"replicas":0}}' --dry-run=server
```

最后一条命令失败是正确结果；它不应修改现有实例。若实例创建时报资源类型不存在，确认 CRD 名称、group、version，并等待 `Established`。本题没有 controller，因此 `readyReplicas: 2` 是为测试 status 子资源手动写入的示例状态。

## 本次答题结果

**答题日期：** 2026-11-14

**判定：** 部分正确，CRD 和实例规格符合要求，但状态子资源的实际写入结果未完成。

以下记录依据答题完成后的集群实际对象和服务端 dry-run 验证整理：

1. CRD `widgets.lab.cka.example` 已达到 `Established`，group 为 `lab.cka.example`，版本为 `v1`，scope 为 `Namespaced`，Kind 为 `Widget`，复数资源名为 `widgets`。
2. 结构化 schema 将 `spec.image` 定义为 `minLength: 1` 的字符串，将 `spec.replicas` 定义为最小值 1、最大值 5 的整数，并把这两个字段列为必填。
3. `status.readyReplicas` 已声明为最小值 0 的整数，`/status` 子资源已启用。
4. `additionalPrinterColumns` 正确配置 `Desired` 列并指向 `.spec.replicas`；实际执行 `kubectl -n cka-ext get widgets` 显示 `demo` 的 `DESIRED` 为 3。
5. 实际 `Widget/demo` 的 `spec.image` 为 `nginx:1.27.5`，`spec.replicas` 为 3，符合实例要求。
6. 使用 `--dry-run=server` 将 `spec.replicas` 改为 0 时，API Server 正确拒绝并报告 `spec.replicas in body should be greater than or equal to 1`；实际实例仍保持 3。
7. `cka-ext` 命名空间中没有 Deployment 或 Pod，未创建 controller，符合限制。
8. 实际 `Widget/demo` 的 YAML 中没有 `status` 字段，`status.readyReplicas` 未设置为题目要求的 2，因此最终状态验收未通过。

本次作答正确定义了 CRD、字段校验、打印列和实例规格，但仍需通过 `kubectl -n cka-ext patch widget demo --subresource=status --type=merge -p='{"status":{"readyReplicas":2}}'` 写入状态。启用 status 子资源后，仅在普通清单或主资源请求中声明 `status` 不能替代该子资源写入。

补充说明：题目目录中的 `demo.yaml` 是第七题 `backend` Pod 的导出内容，不是本题资源；本题 Widget 实例清单位于 `crd-demo.yaml`。该文件问题不影响上述基于实际集群状态作出的判定。
