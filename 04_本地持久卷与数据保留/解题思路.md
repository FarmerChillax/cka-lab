# 第 4 题：解题思路与答案详解

## 关键技术难点

1. `local` PV 必须指定 `nodeAffinity`；调度器会据此把消费该 PV 的 Pod 放到对应节点。
2. 显式写 `storageClassName: ""`，避免 PVC 被默认 StorageClass 接管。PVC 的 `volumeName` 指向目标静态 PV。
3. `Retain` 管理的是 PVC 释放后 PV 的回收行为；Pod 重建期间 PVC 不应删除，数据来自节点本地目录。

## 解题思路

先确认节点和目录，再创建 PV、PVC、Pod；等待绑定与 Pod Running；写文件，删除并重建 Pod，最后读取文件验证。

## 答案详解

将下面清单保存为临时文件 `archive.yaml`：

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: archive-pv
spec:
  capacity:
    storage: 1Gi
  volumeMode: Filesystem
  accessModes:
  - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  storageClassName: ""
  local:
    path: /var/local/cka-archive
  nodeAffinity:
    required:
      nodeSelectorTerms:
      - matchExpressions:
        - key: kubernetes.io/hostname
          operator: In
          values: [cka-lab-worker]
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: archive-claim
  namespace: cka-storage
spec:
  accessModes:
  - ReadWriteOnce
  storageClassName: ""
  volumeName: archive-pv
  resources:
    requests:
      storage: 512Mi
---
apiVersion: v1
kind: Pod
metadata:
  name: archive-check
  namespace: cka-storage
spec:
  containers:
  - name: check
    image: busybox:1.36
    command: ["sh", "-c", "sleep 36000"]
    volumeMounts:
    - name: archive
      mountPath: /data
  volumes:
  - name: archive
    persistentVolumeClaim:
      claimName: archive-claim
```

执行并验证：

```sh
kubectl apply -f archive.yaml
kubectl -n cka-storage wait --for=condition=Ready pod/archive-check --timeout=120s
kubectl get pv archive-pv
kubectl -n cka-storage get pvc archive-claim
kubectl -n cka-storage get pod archive-check -o wide
kubectl -n cka-storage exec archive-check -- sh -c 'printf "cka-archive-ok\n" > /data/check.txt'
kubectl -n cka-storage delete pod archive-check --wait=true
kubectl apply -f archive.yaml
kubectl -n cka-storage wait --for=condition=Ready pod/archive-check --timeout=120s
kubectl -n cka-storage exec archive-check -- cat /data/check.txt
```

再次应用清单时 PV/PVC 保持原样，只有 Pod 被重建。应看到 `Bound`、Pod 节点 `cka-lab-worker`、文件内容 `cka-archive-ok`。若 Pod `Pending`，查看 `kubectl -n cka-storage describe pod archive-check` 中的调度事件，并核对 PV 节点亲和性与 PVC 绑定状态。若 Pod 已调度但无法挂载，检查节点容器内目录是否存在。

## 本次答题结果

**答题日期：** 2026-11-11

**判定：** 部分正确，未满足全部验收条件。

以下记录依据答题完成后的集群实际状态和节点数据整理：

1. PV `archive-pv` 的容量为 `1Gi`，访问模式为 `ReadWriteOnce`，回收策略为 `Retain`，`storageClassName` 为空字符串，未使用默认 StorageClass 或动态供给。
2. PV 使用本地路径 `/var/local/cka-archive`，并通过必需的节点亲和性限定到 `cka-lab-worker`；当前状态为 `Bound`。
3. PVC `cka-storage/archive-claim` 请求 `512Mi`，访问模式为 `ReadWriteOnce`，`storageClassName` 为空字符串，并通过 `volumeName: archive-pv` 绑定目标 PV；当前状态为 `Bound`。
4. Pod `archive-check` 使用 `busybox:1.36`，将 PVC `archive-claim` 挂载到 `/data`，并调度到 `cka-lab-worker`，这些配置符合要求。
5. Pod 的容器命令只有 `echo 'cka-archive-ok' > /data/check.txt`，命令执行成功后立即退出。Pod 使用默认的 `restartPolicy: Always`，检查时处于 `CrashLoopBackOff`，重启次数为 5，未满足保持 Running 的要求。
6. 直接只读检查 `cka-lab-worker` 节点目录，确认 `/var/local/cka-archive/check.txt` 的内容为 `cka-archive-ok`，说明数据已经正确写入。
7. 题面要求的 `kubectl -n cka-storage exec archive-check -- cat /data/check.txt` 实际执行失败，错误为 `container not found ("archive-check")`，因此最终读取验收未通过。

本次作答正确完成了静态本地 PV、PVC 绑定、节点限制、挂载和数据写入，但业务 Pod 没有保持运行。需要让容器执行持续运行的命令，再在 Pod Ready 后写入和读取文件，并重新验证删除、重建 Pod 后的数据保留；仅执行一次写文件命令无法满足本题的 Running 和读取验收条件。

## 复验结果

**复验日期：** 2026-11-11

**判定：** 正确，修改后的 Pod 已满足全部验收条件。

1. Pod 清单中的容器命令已改为 `/bin/sh -c "sleep 360000"`，不再因写文件命令结束而退出。
2. 实际 Pod 的 UID 已由首次检查时的 `ee66a644-4125-4133-8843-f5c73032b085` 变为 `2f27dc7c-6a51-4c98-857c-9e986bf7d9ba`，可以确认 Pod 已在两次检查之间重建。
3. 新 Pod 当前为 `1/1 Running`，重启次数为 0，运行在 `cka-lab-worker`，并继续挂载 PVC `archive-claim` 到 `/data`。
4. PV `archive-pv` 和 PVC `archive-claim` 均保持 `Bound`，原有静态卷配置与绑定关系未改变。
5. 在新 Pod 中执行 `kubectl -n cka-storage exec archive-check -- cat /data/check.txt`，实际输出 `cka-archive-ok`，证明 Pod 重建后数据仍然可读。

首次检查发现的 `CrashLoopBackOff` 问题已消除，静态本地卷、Pod 运行状态及重建后的数据保留均通过复验，最终答题结果以本次记录为准。
