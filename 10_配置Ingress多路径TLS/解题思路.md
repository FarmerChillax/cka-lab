# 第 10 题：解题思路与答案详解

## 关键技术难点

1. Ingress 只有在 `ingressClassName` 与已安装控制器匹配时才会被处理。
2. 更长的 `/api` Prefix 路径应与根路径同时存在，并可分别使用数字端口和具名端口。
3. TLS Secret 必须包含匹配的 `tls.crt`、`tls.key`，Ingress 的 `tls.hosts` 与规则主机应一致。

## 解题思路

先生成并检查证书，再用 `kubectl create secret tls` 创建标准 TLS Secret。随后编写一个同时包含 TLS、两条路径和重定向注解的 Ingress，最后从集群内绕过本机端口映射直接访问控制器 Service。

## 答案详解

```sh
openssl req -x509 -nodes -newkey rsa:2048 -days 30 \
  -keyout /tmp/portal.cka.local.key \
  -out /tmp/portal.cka.local.crt \
  -config tls/openssl.cnf
openssl x509 -in /tmp/portal.cka.local.crt -noout -subject -ext subjectAltName
kubectl -n cka-edge create secret tls portal-tls \
  --cert=/tmp/portal.cka.local.crt --key=/tmp/portal.cka.local.key
```

保存并应用 `portal-ingress.yaml`：

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: portal
  namespace: cka-edge
  annotations:
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
spec:
  ingressClassName: nginx
  tls:
  - hosts:
    - portal.cka.local
    secretName: portal-tls
  rules:
  - host: portal.cka.local
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: api-svc
            port:
              number: 8080
      - path: /
        pathType: Prefix
        backend:
          service:
            name: web-svc
            port:
              name: http
```

```sh
kubectl apply -f portal-ingress.yaml
kubectl -n cka-edge describe ingress portal
```

运行题面验收命令。若返回默认 404，优先检查请求的 `Host`、`ingressClassName` 和规则主机；若出现 503，检查 Service 端口及 EndpointSlice；TLS 失败时检查 Secret 类型、键名和证书私钥是否匹配。

## 本次答题结果

**答题日期：** 2026-11-19

**判定：** 部分正确。路径路由、TLS Secret 和证书材料均符合要求，但 Ingress 规则缺少 `host`，导致控制器没有为 `portal.cka.local` 使用 `portal-tls` 证书，实际 HTTPS 返回默认假证书。

### 已满足项

1. `Secret/portal-tls` 位于 `cka-edge`，类型为 `kubernetes.io/tls`，包含 `tls.crt` 和 `tls.key` 两个键。
2. 证书为自签名证书，`subject` 和 `issuer` 均为 `CN=portal.cka.local, O=CKA Lab`，SAN 包含 `DNS:portal.cka.local`。
3. 证书有效期为 2026-11-19 至 2026-12-19，共 30 天；公钥为 RSA 2048 位。
4. `Ingress/portal` 位于 `cka-edge`，`ingressClassName` 为 `nginx`，注解 `nginx.ingress.kubernetes.io/ssl-redirect` 的值为字符串 `"true"`。
5. `/api` 使用 `Prefix` 匹配并转发到 `api-svc` 的数字端口 `8080`；`/` 使用 `Prefix` 匹配并转发到 `web-svc` 的具名端口 `http`。
6. 通过本地端口转发等价验证，`https://portal.cka.local/api` 返回 `api-backend`，`https://portal.cka.local/` 返回 `web-backend`。
7. ingress-nginx 控制器为 `1/1` 可用，`web` 和 `api` Deployment 均为 `2/2` 可用；两个 Service 的端口配置与初始环境一致。

### 未满足项与观察

1. 本地 `ingress.yaml` 和集群中的 `Ingress/portal` 都没有在 `spec.rules[]` 下设置 `host: portal.cka.local`。当前规则会匹配所有主机，而不是题面要求的指定主机。
2. 控制器生成的 `nginx.conf` 中只有默认 `server_name "_"`，没有出现 `portal.cka.local` 的专用 server。
3. 使用 SNI `portal.cka.local` 访问 HTTPS 时，实际返回证书为 `O=Acme Co, CN=Kubernetes Ingress Controller Fake Certificate`，不是 `portal-tls` 中的证书。因此“为该主机终止 TLS”未真正生效。
4. 题面验收命令使用 `--no-check-certificate`，只验证路由和 HTTPS 可访问，不会发现服务端返回了默认假证书。
5. 额外观察：携带 `Host: portal.cka.local` 的 HTTP 请求返回 `200`，未观察到重定向。虽然注解值符合题面要求，但当前 hostless 规则下重定向行为并未生效。
6. 本地 `ingress.yaml` 未显式声明 `metadata.namespace`；集群资源实际位于 `cka-edge`，应是应用时通过命名空间参数指定。建议清单中补全命名空间，提高可复现性。
7. 初始 `ingress-probe` 的命令只有 `sleep 3600`，长时间后容器已过期并处于 `Completed`，导致原验收第二条命令无法执行。本次使用端口转发完成等价验证；这是环境探测 Pod 生命周期问题，不是答题资源错误。

### 修正方向

在 `spec.rules[]` 中补上：

```yaml
host: portal.cka.local
```

重新应用后，应再次验证：

1. 控制器配置中出现 `portal.cka.local` 对应的 server。
2. 使用 SNI `portal.cka.local` 访问时，服务端证书 CN/SAN 为 `portal.cka.local`，而不是 Fake Certificate。
3. HTTP 请求能够按 `ssl-redirect` 注解重定向到 HTTPS。
4. `/api` 和 `/` 仍分别返回 `api-backend`、`web-backend`。

另外，`tls.key` 是私钥，不应提交到 Git。

## 本次学习收获

1. **Ingress 三角色**：Ingress 是路由规则，IngressClass 是规则与控制器之间的桥梁，Ingress Controller 才是真正监听请求、终止 TLS 和转发流量的组件。
2. **IngressClass 匹配链**：`Ingress.spec.ingressClassName` 指向 IngressClass 名称，IngressClass 的 `spec.controller` 再匹配控制器启动参数中的 `--controller-class`。
3. **路径匹配**：`pathType: Prefix` 按路径段匹配，`/api` 可匹配 `/api/users`，但不匹配 `/apix`；多个路径匹配时更长路径优先。
4. **Service 端口与 targetPort**：Ingress 引用的是 Service 的 `port`，不是 Pod 的 `targetPort`。本题 `api-svc` 应引用 `8080`，后端 Pod 实际监听 `80`。
5. **具名端口**：Service 端口可以有名字，Ingress 可通过 `port.name` 引用，例如本题 `web-svc` 的 `http`。
6. **TLS 基本目标**：TLS 提供机密性、完整性和身份认证。HTTPS 可以理解为 HTTP over TLS。
7. **对称与非对称加密**：非对称加密用于身份认证和密钥协商，握手后的应用数据主要使用对称加密保护。
8. **证书与私钥**：证书包含公钥、域名、有效期、签发者和签名；私钥必须单独保密。证书本身不包含私钥。
9. **CA 信任链**：客户端通过受信任根 CA 验证服务器证书。自签名证书可以加密通信，但默认不被客户端信任。
10. **CN 与 SAN**：现代客户端主要检查 SAN 中的域名。本题证书必须包含 `DNS:portal.cka.local`。
11. **SNI 与 Host**：SNI 在 TLS 握手阶段用于选择证书，HTTP Host 头在解密后用于 Ingress 路由匹配。两者作用不同。
12. **TLS 终止模式**：本题是客户端到 Controller 使用 HTTPS，Controller 解密后以 HTTP 转发到后端。TLS 透传和重新加密是另外两种模式。
13. **Kubernetes TLS Secret**：Ingress TLS Secret 类型应为 `kubernetes.io/tls`，键名应为 `tls.crt` 和 `tls.key`，并与 Ingress 同命名空间。
14. **openssl 定位**：CKA 不把 openssl 本身作为独立考点，但证书检查、TLS Secret 创建和 kubeadm 证书管理是相关能力。本题用 openssl 生成自签名证书是为了理解证书来源。
15. **验收命令的局限**：`--no-check-certificate` 会跳过证书信任与域名校验，可能掩盖服务端使用默认假证书的问题。更完整的验证应检查实际返回证书的 CN/SAN。
16. **host 字段影响 TLS 和重定向**：只写 `spec.tls.hosts` 而不在 `spec.rules[].host` 中声明主机，可能导致控制器没有为该主机生成专用 server，进而使用默认证书且重定向不生效。
17. **探测 Pod 生命周期**：临时探测 Pod 如果使用有限时长 sleep，长时间后会退出；复验时需要确认探测容器仍 Running，或使用等价方式验证。
